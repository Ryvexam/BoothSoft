# Guest UI, theme artwork and resource budget

## Guest journey

The **live view is the booth's normal state**: the app starts there and every
session ends there (`Ready` → `Countdown` → flash → `Processing` → `Review` →
`Thanks` → `Ready`). Retake returns to `Ready` within the same session.
The attract screen (`Welcome`) is only the **sleep screen** ("veille"): shown
after `sleep_minutes` (default 5) with no touch *and* no presence in front of
the camera. While asleep the camera decodes 4 frames/s, displays nothing
(~1 % CPU) and `camera::PresenceDetector` wakes the booth when someone walks
up (`wake_on_motion`, default on); a tap wakes it too.

* **Welcome (sleep)**: full-screen theme artwork; a tap anywhere returns to the live view.
* **Ready**: mirrored live view (30 FPS by default), print-crop guide (areas the
  print will cut are shaded), round shutter, close button, and six **live filter
  thumbnails** (Naturel, Éclat, Doux, N&B, Sépia, Vintage), three on each side of
  the shutter, each showing the camera through its own filter.
* **Countdown**: one ring segment per second, numeral + guidance ("Souriez !").
* **Review** (modelled on dslrBooth's sharing screen): the print, frame included,
  fills the screen above a single action bar (Reprendre · Imprimer / Photo
  suivante / Terminer), over a blurred copy of itself (32 px box-average upscaled
  to 256 px once per photo: no real blur pass). Auto-return hint only in the last 15 s.
* **Thanks**: the guest's print shown as a tilted instant photo.
* **Welcome status chips** (top right): event name and prints left for the
  event (`maximum − confirmed − queued`); accent colour under 10 %.
* **Maintenance**: Ctrl+Shift+D, or **5 quick taps** on the logo chip of the live
  view (or the top-right corner of the sleep screen). The PIN is still required.

## Events, burst mode, start-up

* **Events** (Maintenance → Événements): a planning of named events with a date
  and hours (`end` ≤ `start` = runs past midnight). The event covering the
  current time is used automatically, otherwise the default event. Photos are
  stored per event: `sessions/<date>-<nom>/<séance>/photo-NN.jpg` with the
  printed version `photo-NN-cadre.jpg` next to it. The print quota and the
  session limit apply per event. Sessions saved before this change stay readable
  from `sessions/<séance>/`.
* **Burst mode** ("rafale", 3–10 photos): one countdown, then one photo every
  0.9 s with a different pose prompt, then a picker: big selected photo
  (swipe or arrows), copies per photo (0 = not printed), filmstrip with copy
  badges, "Imprimer N tirages" (confirmation above 3). Memory: thumbnails
  420 px + one full-size texture decoded on selection (+~15 MB, released when
  the session ends).
* **Start with the computer** (Caméra & écran): per-user start-up entry
  (Windows `HKCU\…\Run`, macOS LaunchAgent, Linux XDG autostart). The app opens
  full screen on the live view of the scheduled event. For an unattended booth
  also enable Windows automatic sign-in and disable sleep / screen saver.

## Theme manifest additions (all optional, backwards compatible)

```toml
[assets]
background = "assets/background.png"   # welcome artwork, drawn "cover"

[ui]
print_label = "Imprimer"
start_label = "C’est parti"
welcome_eyebrow = "Photobooth"
welcome_title = "Des souvenirs\ngrandeur nature"   # \n = line break, 140 chars max
welcome_subtitle = "On appuie, on sourit, c’est imprimé."
thanks_title = "Merci !"
thanks_subtitle = "Votre photo vous attend, à très vite devant l’objectif !"
```

The `frame` PNG is the print overlay: opaque border, transparent photo area,
composited in software over the photo. Bundled frames are 1800×1200
(6×4 in at 300 DPI). Colours: `primary` = titles, `accent` = call to action,
`background`/`foreground` = review and thanks screens (dark themes work).

Artwork for the bundled theme (`default`, shown as "Party")
is generated by `scripts/theme-art/generate.py THEMES_DIR` (Pillow + numpy, OFL
fonts in `scripts/theme-art/fonts`).

## Rendering and resource rules

* **Touch-first motion** (`ui.rs`, "motion"): every tap answers within one frame and
  every change of state is shown by a short movement (≤ 250 ms, ease-out):
  buttons sink under the finger, the "Une photo / Rafale" pill glides, screens
  and modals slide in, the print zooms onto the review, the burst photo follows
  the finger and flips with a rubber band at both ends, the countdown numeral
  pops each second. Helpers `appear` / `glide` / `press` request repaints only
  while a transition runs.
* No *continuous* animation: nothing loops. Idle screens request **no repaint** (0 % CPU,
  re-measured after the motion work: 0.0 % on live, picker and maintenance).
  Countdown repaints once per second, the flash in six 60 ms steps,
  Review once per second only during its last 15 s.
* Live view (`src/kiosk/live_gl.rs`): the decoded RGB frame is uploaded as-is
  into an OpenGL texture; filter (3×3 colour matrix), mirror and cover crop run
  in a fragment shader. No CPU downscale, filter loop, RGBA conversion or
  per-frame allocation. Displayed buffers are recycled to the camera thread
  (bounded channel). Falls back to egui textures if GL init fails
  (`BOOTHSOFT_LIVE_CPU=1` forces the fallback).
* Resampling uses `fast_image_resize` (SIMD u8) instead of `image::imageops::resize`
  (f32 intermediate buffers). `imageops::thumbnail` (which ignores aspect ratio
  and distorted previews) is no longer used for photos.
* Countdown numerals are rasterised alone into a small texture (`ui::BigNumeral`)
  instead of growing egui's shared font atlas (+24 MB measured).
* Linux/glibc: fixed `M_MMAP_THRESHOLD` so freed photo buffers return to the OS.

## Without a GPU (software OpenGL)

Every displayed frame is then rendered by the CPU, and the cost is dominated by
the *number of frames presented*, not by what is drawn (a blank frame costs
almost as much as the full UI). Measures taken for this case:

* egui turns a zero-delay `request_repaint()` into two frames; worker wake-ups
  now use a 1 ms delay, so one camera frame = one repaint (was two).
* `LP_NUM_THREADS=1` is set at start-up unless already set: llvmpipe's thread
  pool costs more than it saves for this scene. GPU drivers ignore it.
* The full-screen camera quad is opaque: no blending, no per-pixel corner maths.
* `live_fps` setting (Maintenance → "Fluidité du live", 10–30, default 30) and a
  renderer line in Maintenance ("Rendu : GPU …" / "Rendu : logiciel …").
  `BOOTHSOFT_FPS_LOG=1` prints the real repaint rate.

Profiling (gdb stack sampling + per-layer toggles) showed the main thread
spends its time waiting in `SwapBuffers` for llvmpipe: what costs is pixels
rasterised per frame. Per-layer cost at 30 FPS before the last round:
camera quad ~29 %, vignettes + print-crop shading ~13 %, useless full-screen
fills ~5–10 %, chrome + filter strip ~9 %, clear + present ~3.5 %.

Applied, in order of gain:

1. No full-screen fills under the camera (panel fill, placeholder background).
2. Vignettes, print-crop shading and countdown dimming computed **inside the
   camera shader** (one opaque pass instead of three blended layers).
3. Nearest sampling for the camera texture when OpenGL is software-rendered and
   the image is shown near 1:1 (≤ x1.3); bilinear otherwise and always on a GPU.
4. No blurred shadows / translucent discs on per-frame elements (thumbnails, shutter).
5. MJPEG decoded by our own libjpeg-turbo path (`src/mjpeg.rs`): integer-fast
   IDCT and plain chroma upsampling for the live view, accurate settings for the
   captured photo; output RGBA so texture uploads are plain copies.

Live view, synthetic 1280×720 MJPEG camera at 30 FPS, llvmpipe, 2 vCPU cloud machine:

| | CPU | Reached FPS |
| --- | --- | --- |
| First 30 FPS version | 171 % | ~25 |
| + one repaint per frame, 1 llvmpipe thread, opaque quad | 97 % | 30 |
| + shader overlays, no fills, nearest, lighter chrome, fast MJPEG | **48 %** | 30 |

Breakdown now: llvmpipe 34 %, UI thread 8 %, camera decode 6.5 %.

### Floor analysis and motion gate

Isolating the camera layer (upload alone ~1.6 %, drawing ~18–20 %) and trying a
1:1 `glBlitFramebuffer` (−1.8 % only) and a texture-only shader (−5 %, without
filters) showed the camera quad already runs at llvmpipe's raw fill rate:
drawing 1 Mpx per frame differently does not make it cheaper. Disabling egui
feathering would save ~4.6 % but makes edges jagged: rejected.

The remaining lever is drawing fewer frames when nothing changes.
`camera::MotionGate` summarises each decoded frame as a 16×9 grid of mean luma
(~3.6 k sampled pixels) and displays it only if a cell moved by more than 3
levels since the last displayed frame, with a 10 FPS keep-alive. Movement is
always shown at the full rate; a frozen pose or an empty booth looks identical.

| Synthetic camera, 30 FPS, no GPU | CPU | Repaints/s |
| --- | --- | --- |
| Moving scene | 48 % | 30 |
| Still scene with sensor noise (`BOOTHSOFT_SYNTHETIC_CAMERA=static`) | **19 %** | ~8 |
With a GPU the llvmpipe line disappears (app ≈ 15 % of one core at 30 FPS).

### Robustness fix

libjpeg-turbo reports corrupt data by unwinding out of a C callback. With the
former `panic = "abort"` release profile, **one truncated USB MJPEG frame
aborted the whole kiosk**. The release profile now uses `panic = "unwind"` and
`mjpeg::decode` catches it: the frame is dropped, the live view continues.

Windows machines with no GPU driver only expose OpenGL 1.1 (GDI), which eframe's
glow backend cannot use; ship Mesa's `opengl32.dll` (llvmpipe) next to the
executable, or move to eframe's wgpu backend (DX12 WARP). Not tested here.

On real hardware the rasteriser line moves to the GPU; the application's CPU
cost during live view is the first two lines. Not yet measured on macOS or
Windows devices, or with a physical camera.

## Target booth PC

Intel Core i5 4th/5th gen, 8 GB RAM: its integrated Intel HD 4600/5500 supports
OpenGL 4.x, so the GPU live-view path is used (software rendering only applies
without a working graphics driver). `scripts/build-booth.sh` builds with
`-C target-cpu=haswell` for that machine.
